# AutoReport 面试准备指南

> 目标：把「AutoReport 多智能体自动研报系统」从一份代码变成一场能打的有准备之战。
> 原则：每一个设计选择都能回答"为什么这样做、还考虑过什么替代方案、踩过什么坑"。

---

## 1. 项目简介（按场合选择版本）

### 30 秒电梯演讲

> AutoReport 是一个基于 LangChain 1.x + LangGraph 的 A 股研报自动分析系统：自动采集研报 PDF，解析入库后做「向量语义 + 关键词」混合检索，由多智能体协作生成带引用溯源的投资研究报告。整个系统强调工程化——幂等入库、人机协同、评测闭环、无 Key 全链路降级，配有 29 个单元测试和 Docker 一键部署。

### 2 分钟展开版（结构：背景 → 难点 → 方案 → 结果）

> 我做这个项目的起点是一个真实痛点：个人投资者面对海量卖方研报，想交叉验证一个观点要在几十份 PDF 里翻。所以我做了一个流水线：东财/巨潮采集器自动抓研报和年报公告 → PDF 解析、规则+LLM 双通道元数据抽取、页级分块入 SQLite+Chroma → 检索层针对金融场景做了实体抽取加双通道 RRF 融合 → LangGraph 编排「主管-研究员-工具员-写作」四个角色生成报告。
>
> 三个我认为最有含金量的点：一是**引用溯源机制**——引用编号在检索时确定，写作 Agent 只能用已有编号，从机制上杜绝编造来源；二是**人机协同**——用 LangGraph 的 interrupt 在生成前挂起等人工确认计划，SqliteSaver 检查点保证挂起状态可持久化；三是**评测闭环**——评测集从真实入库研报自动生成，gold 零标注成本，可以量化每次优化。
>
> 工程上：全程优雅降级（没有 API Key 也能跑通检索和引用），29 个单元测试，Docker Compose 一键起。

### 关键数字（背下来）

| 项 | 数字 |
|---|---|
| 源码规模 | 42 个 Python 文件 / 约 3400 行（src），另有 300 行测试 |

## 2. 架构与数据流（白板上要会画）

```
数据层    inbox PDF ─┐                      ┌─ 报告表(元数据/状态机)
          东财采集 ──┤→ PDF解析 → 元数据抽取 →├─ 分块表+FTS5(jieba)
          巨潮公告 ──┘   (PyMuPDF) (规则+LLM) └─ Chroma 向量库
检索层    问题 → 实体抽取(代码/名称/指标) → [向量通道(代码过滤) ‖ FTS关键词]
              → RRF 融合 → 业务重排(实体加分+日期衰减) → 带引用上下文
智能体层  supervisor(结构化拆解) → plan_gate(interrupt 人工确认)
              → 循环调度 researcher(检索ReAct) / tool_agent(计算·核对·联网)
              → writer(引用白名单写作) → Markdown 研报
观测层    LangSmith 全链路 trace（无 Key 降级本地日志）+ 评测闭环
```

**一句话讲清每个分层职责**：数据层管「可靠的入库」，检索层管「找得准」，智能体层管「想得清、写得对」，观测层管「可测量、可迭代」。

## 3. 技术亮点（每个按「问题→方案→为什么→追问」准备）

### 3.1 混合检索：双通道 + RRF + 业务重排

- **问题**：研报问答是「实体+事实型」（"600519 最新评级"），纯向量检索会把语义相近但**股票不对**的内容排前面。
- **方案**：查询先过实体抽取（6 位代码校验、名称含"末两字简称"启发式、指标词表）→ 向量通道带 `stock_code` where 过滤召回；FTS5(jieba) 关键词通道兜底精确匹配 → **RRF**（Reciprocal Rank Fusion，k=60）融合两路排名 → 业务重排：实体命中 +0.35 硬信号、指标词命中 +0.05/个、日期新鲜度最多 +0.15。
- **为什么 RRF**：两路分数量纲不同（cosine 距离 vs BM25 分），直接加权需要调参且不稳；RRF 只用排名，1/(k+rank) 简单稳定。
- **可能的追问**：
  - *"为什么不 rerank 模型（bge-reranker）？"* —— 认可这是标准做法，但本地 rerank 需要 GPU/额外依赖，当前用业务规则重排在实体型查询上更可控；这是评测驱动下可以加的下一步。
  - *"向量通道没 Key 时怎么办？"* —— try/except 降级到纯关键词，检索永不 500。

### 3.2 引用溯源：编号白名单防幻觉（机制而非提示词）

- **方案**：`CitationManager` 在检索阶段为「报告+页码」分配全局编号；上下文里每段末尾带 `[n]`；写作 prompt 里注入「可用引用清单」并**禁止使用清单外编号**。
- **关键设计观**：防幻觉靠的是**让编造在结构上不可能**，而不是"请勿编造"的提示词——模型编一个 `[99]`，引用列表里没有 99，一眼识破。
- **追问**：*"模型还是可能张冠李戴把 [1] 的话安到 [2] 上？"* —— 承认 LLM 判定无法 100%，所以评测体系里有「引用正确率」客观指标 + 人工抽检；多智能体分工（研究员只总结、写作只汇编）也在缩小出错面。

### 3.3 LangGraph 多智能体：状态黑板 + 循环调度 + HITL

- **图**：`supervisor → plan_gate(interrupt) → route ⇄ researcher/tool_agent → writer → END`。
- **三个值得讲的细节**：
  1. **状态设计**：`findings`/`citations` 用 `operator.add` reducer 追加（多节点并行产出安全合并），其余字段 last-value-wins；state 里只放可序列化对象，保证 SqliteSaver 持久化。
  2. **为什么 researcher 和 tool_agent 分两个节点**：职责单一——检索型与计算/核对型的系统提示词和工具集完全不同，混在一起会稀释约束、增加工具误选；图上一目了然、可独立评测。
  3. **HITL**：`interrupt()` 挂起，CLI/UI 用 `Command(resume=计划/False)` 恢复；人工可以直接改计划再继续——高价值产出的「方向错误」在执行前被挡住。
- **追问**：*"为什么不用 AutoGen/CrewAI？"* —— 研报生成是**有固定流程骨架、局部需要自主性**的任务，StateGraph 显式编排可控可调试；全自由对话式多智能体不适合结构化产出。

### 3.4 结构化输出任务拆解

- `with_structured_output(Pydantic模型)`：schema 同时当「提示词」和「校验器」；拆解失败自动重试一次，再失败降级为默认单步检索计划。
- **观点**：主管是「尽力优化」而非「必要依赖」——这是整个系统降级哲学的一部分。

### 3.5 安全计算器：AST 白名单

- LLM tokenizer 对数字不友好，算术必须外置。用 `ast.parse` 白名单求值（只放行四则/幂/一元符号），**模型输出永远不直接进解释器**——这是把"LLM 生成不可信"当威胁模型处理。
- 追问 *"为什么不用 eval？"* —— eval 能执行任意代码；为什么不用 numexpr？—— 少一个依赖，AST 30 行可控可测。

### 3.6 公告交叉核对（金融领域特有的可信度增强）

- 工具 `verify_with_announcement`：用巨潮官方年报 PDF 抽取「营业收入/归母净利润」实际值，与研报预测值对比（统一换算亿元、±5% 内视为基本一致）。
- **讲点**：研报是卖方观点，官方公告是第二信源；抽取失败时工具明确返回"证据不足，请勿声称已核对"——工具的设计哲学是**永不抛异常，把失败当普通文本结果让模型自行换路径**。

### 3.7 幂等入库与状态机

- `pdf_hash(sha256)` 唯一键：重复导入直接跳过；`pending → parsed → indexed` 状态落库，向量化失败不回滚结构化入库（保留关键词检索能力）；采集器已有结构化元数据时走「API 优先于解析」覆盖。
- **讲点**：批处理 + 断点续跑 + 可统计，是数据工程的肌肉记忆。

### 3.8 评测闭环：让优化有数字

- 评测集从真实入库研报**自动生成**（gold=元数据推导，零标注成本），允许人工补充；
- 三指标：检索命中率@5（gold 报告进 Top-5）/ 引用正确率（回答中 `[n]` 是否都在合法清单——**程序判定，完全客观**）/ LLM-as-judge 1-5 分（small 模型控成本，≥3 视为合格）；
- 产出 JSONL（逐条明细，支持优化前后回归对比）+ Markdown 报告（含失败案例清单，直接指出优化方向）。
- **观点**：judge 有噪声，所以目标定 90% 不是 100%，且保留人工抽检——对 LLM-as-judge 的局限有清醒认识。

### 3.9 优雅降级体系（面试官问"没 Key 能跑吗"时的满分答案）

| 依赖缺失 | 系统行为 |
|---|---|
| 无 LLM Key | 问答降级为"最相关原文片段+引用"；研报生成报清晰错误；检索/评测客观指标照常 |
| 无嵌入 Key | 纯 FTS 关键词检索（评测基线命中率已可测量） |
| 无 LangSmith Key | 本地 JSONL/Markdown 报告 |
| 无 Tavily Key | web 工具返回提示文本，Agent 自主改用本地库 |
| 单个子任务失败 | 写 `state.error` 路由直接终止，不炸整图 |

### 3.10 工程化交付

uv（锁文件可复现）/ Docker 依赖层缓存（改代码不重装依赖）/ .env 单一配置入口（pydantic-settings 强类型，错误启动时暴露）/ typer CLI / Streamlit Demo（AppTest 冒烟）/ git 历史干净（每个 Phase 一个 commit，消息即 changelog）。

## 4. 设计思路总纲（回答"为什么这么分层"）

1. **配置即代码边界**：所有密钥/开关收敛在 `.env` + `config.py`，业务代码零感知提供商——切 Qwen/DeepSeek 只改一行。
2. **LLM 工厂 + 模型分级**：`get_chat_model("main"/"small")`，规划写作用大模型、抽取判分用小模型——token 成本控制第一手段。
3. **轻链路/重链路分离**：`ask`（一次检索+一次生成，低延迟）与 `report`（多智能体+HITL，深度）共用同一检索与引用层——能力复用，体验分层。
4. **每个节点都"可测试"**：节点函数都是 `state→dict` 纯函数，图级测试不需要 mock LLM——降级路径本身就是测试对象。

## 5. 开发难点解析（真实踩坑，"做过"的最强证明）

> 这部分是面试差异化关键：背得出来的知识点人人会讲，踩过的坑只有真做过的人有。

### 5.1 langgraph-checkpoint 4.x 与 langgraph-checkpoint-sqlite 2.0.10 的序列化断层

- **现象**：图跑到 checkpoint 写入时报 `AttributeError: 'JsonPlusSerializer' object has no attribute 'dumps'`。
- **定位**：读两包源码——checkpoint 4.x 把 `JsonPlusSerializer.dumps/loads` 移除只留 `dumps_typed/loads_typed`，而 sqlite saver 的 metadata 序列化还在调旧 API（channel 数据走新 API 无恙）。
- **解决**：不 fork 不降级（锁文件冲突），写 metadata 序列化兼容层（ormsgpack 直封）替换 `saver.jsonplus_serde`，生产与测试共用一个工厂函数。
- **升华**：快速拉满新版本依赖是要付代价的；兼容层 20 行换回升级自由，划算。

### 5.2 DeepSeek 不支持 json_schema 结构化输出

- **现象**：`with_structured_output(Pydantic模型)` 调 DeepSeek 报 400 `This response_format type is unavailable now`——langchain 默认走 `json_schema` response_format，DeepSeek 只支持 `json_object`。
- **解决**：写了统一的 `structured_invoke()`：`response_format={"type":"json_object"}` + 把 Pydantic schema 显式注入 prompt + `model_validate_json` 校验 + 剥代码围栏。Qwen/DeepSeek 通吃。
- **升华**：OpenAI 兼容 ≠ 功能全兼容；「兼容层」要建立在实测之上（同项目此前 Qwen/DeepSeek 切换设计因此受益——一处修复全局生效）。

### 5.3 东财研报列表 API 的 400

- **现象**：参数拼对仍 400。**定位**：对照浏览器请求逐项 diff——需要 `pageNo`（不是 `pageIndex`）+ `industryCode=*` 等占位参数 + `Referer: https://data.eastmoney.com/report/` 头。
- **升华**：爬虫调试方法论：抓真实请求 → 最小 diff → 逐项回放。以及尊重目标站点：限速、UA 声明身份、robots 检查。

### 5.4 interrupt 状态必须可序列化

- 设计 state 时一度想把 `CitationManager` 实例直接放进图状态（共享编号最优雅），意识到 SqliteSaver 要把 state 写盘、HITL 挂起可能跨进程恢复后，改为「编号偏移法」：每个子任务持独立 manager，`start_from=已有引用数+1`。代价是跨任务同页可能重复编号（可接受），换来零序列化风险。
- **升华**：**跨节点的全局可变对象是分布式系统的暗雷**，宁可加一点冗余换取状态可序列化的确定性。

### 5.5 FTS5 中文分词

- SQLite FTS5 默认 unicode61 tokenizer 对中文无效（整句当一个 token）。方案：入库侧用 jieba 分词后再写入 FTS 虚表，查询侧同样分词。评测里命中率明显依赖这一步。
- 权衡：jieba 比 pkuseg 慢但快、准、零依赖——够用哲学。

### 5.6 PyMuPDF 的 import 变更

- 老教程写 `import fitz`，新版本已弃用需 `import pymupdf`。教训：**以官方 changelog 为准，不以博客为准**；扫描件检测（页均文本过少 → `ocr_needed` 标记）让坏数据显式可见而不是静默进库。

### 5.7 Streamlit + LangGraph 长生命周期的资源管理

- `SqliteSaver` 连接必须跨 rerun 复用（Streamlit 每次交互重跑脚本），用 `@st.cache_resource` 缓存编译后的 graph；thread_id 存 `session_state` 保证刷新后还能对同一线程 resume。

### 5.8 循环导入（小坑但真实）

- `evaluation/__init__.py` 同时导出 dataset 与 run_eval，run_eval 又从包命名空间导入 metrics——`__init__` 未完成时会炸。改为 run_eval 直接从子模块导入。教训：包的 `__init__` 保持薄，跨子模块导入走全路径。

## 6. 高频面试问答（按追问概率排序）

### 架构与选型

**Q: 为什么多智能体？单 Agent + 工具不行吗？**
> 单 Agent 能解决 ask；但报告生成有三个单 Agent 做不好的点：①任务天然分相（拆解/调研/计算/写作），混在一个上下文里提示词互相污染；②计划确认 HITL 需要在「执行前」有明确的中断边界；③分角色让每次 LLM 调用的输入更短更聚焦，成本和稳定性都更好。同时我也保留了单链路（ask），按任务复杂度分流。

**Q: 多个 Agent 怎么共享信息？**
> LangGraph 的共享状态（黑板模式）：findings/citations 是 reducer 追加的列表，所有节点读写同一 state；checkpoint 每次 superstep 落盘。相比消息传递（A2A），黑板对"多步汇聚产出一份文档"的场景更直接。

**Q: 如果检索结果不准确，系统怎么自我修正？**
> 三层：研究员 ReAct 循环内可以自己换关键词重查；评测报告的失败案例清单人工驱动参数/分块策略迭代；verify 工具提供第二信源校验。没有做 graph 内自动反思节点（reflexion）——是明确的下一步实验项。

### RAG 细节

**Q: chunk 怎么切？为什么按页？**
> 页级为主、超长页滑窗切分（overlap 保上下文）。按页是因为研报的关键表格/评级框通常整页自洽，且引用粒度"机构+日期+页码"对人类最可回溯；同时结构化元数据（评级/目标价）独立入库不依赖 chunk。

**Q: 怎么处理表格和图表？**
> 坦诚现状：PyMuPDF 抽文本流，复杂表格会有损失；`ocr_needed` 标记扫描件。改进路线是表格转 Markdown（pdfplumber/camelot）+ 多模态模型解析图。

**Q: 检索为什么不用混合权重（如 0.7*vector+0.3*bm25）？**
> 分数量纲不同调参脆弱，RRF 只用排名免调参；业务信号（实体命中/新鲜度）放到重排阶段做显式加分，比在融合里埋权重更可解释、可测试。

**Q: 引用正确率怎么算的？**
> 程序判定：从回答里 re 抽取所有 `[n]`，与引用清单合法编号集合作交并比。没有引用输出的条目不计入（如"库里没有资料"）。这是完全客观、可回归的指标。

### LangSmith / 可观测性

**Q: LangSmith 用在哪？**
> 三处：①`apply_langsmith_env` 全局 trace，每次 LLM/工具调用入图节点都有 span；②评测集自动上传成 dataset；③优化前后的 trace 对比。无 Key 时全部降级为本地日志+本地评测报告。

**Q: 成本怎么控？**
> main/small 双模型分级；researcher 设 recursion_limit 上限；report 字数截断保护；评测记录每条延迟与 token（LangSmith 面板看单次成本）。

### 工程与测试

**Q: 测试怎么做的？LLM 依赖怎么 mock？**
> 29 个测试全部不依赖真实 Key：网络 mock（采集器）、AST 纯函数（calc）、降级路径当被测对象（无 Key 的图级测试断言"清晰错误+正常终止"）、HITL 用内存 sqlite checkpointer 测 interrupt/resume/取消/改计划全流程。哲学：**把降级当一等公民测**。

**Q: 幂等怎么保证？**
> sha256 文件哈希唯一键 + 状态机落库；向量化失败不回滚结构化入库。采集器层面也有标题+日期去重。

**Q: 数据库为什么 SQLite 不用 PG？**
> 单机个人项目，SQLite+FTS5 零运维、备份=复制文件；抽象在 SQLAlchemy 层，升 PG 是换连接串+把 FTS 换 tsvector 的工作量。评测里 SQLite 已足够跑出有意义的数字。

### 金融业务

**Q: 系统生成的报告能直接用吗？**
> 不能，明确说：输出是"结构化资料汇编+引用"，定位是**辅助阅读和交叉验证**，不构成投资建议（README 有免责声明）。报告生成前有人工计划确认，也是把人的判断放进流程。

**Q: verify 工具的数字抽取可靠吗？**
> 年报的"营业收入 xxx 元"版式高度可预期，正则+单位换算（统一亿元）可靠；但抽不到时工具会明确说"证据不足，请勿声称已核对"——把不确定性显式交给上层，比硬编一个数诚实。

## 9. 简历写法建议（STAR 数字化）

> **AutoReport · 多智能体自动研报系统**（个人项目 | Python / LangChain 1.x / LangGraph）
>
> - 基于 LangGraph 编排「主管-研究员-工具员-写作」四角色 Agent，实现研报问答与带**引用溯源**的报告生成；interrupt + SqliteSaver 实现计划人工确认（HITL），状态可持久化、可恢复
> - 设计**混合检索**：实体抽取 + 向量/FTS5(jieba) 双通道 RRF 融合 + 业务重排，解决金融实体型查询的命中率问题；引用编号白名单机制从结构上杜绝 LLM 编造来源
> - 构建**评测闭环**：自动生成 N 条评测集，量化检索命中率@5 / 引用正确率 / LLM-as-judge，以 JSONL 明细支撑"优化前→优化后"回归（跑分后填具体数字，如 71%→93%）
> - 全程**优雅降级**（无 Key 可用）、pdf_hash 幂等入库、29 个单元测试、Docker Compose 一键部署；约 3.4k 行 Python
